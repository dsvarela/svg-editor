# Review, 2026-08-15

Covers the touch retrofit and the three tests fixed before it: sizing under a
coarse pointer, the two-finger gesture, the held-key buttons, and the two strips
that had to start scrolling to hold them.

**What it found: 1 instrument wrong three ways, 1 defect the tests found before
a hand could, 5 tests that could not fail, and 1 line nothing distinguishes.**
The instrument is the finding that matters, because every touch number recorded
before this date was produced by it.

---

## The instrument was wrong, and it had been wrong in public

`tools/touch.mjs` exists because a count in `CLAUDE.md` was once quoted with no
method behind it. The tool was written to be the method. It then drifted, and
because it drifted quietly the numbers it produced were used to decide what to
work on.

Three faults, each found by a different accident:

1. **Collapsed groups were invisible to it.** The rail redesign left eleven
   groups shut by default, a shut group is `hidden`, and a hidden control has no
   box. Found by running the tool and getting 37 where the markup holds 166.
2. **Disabled controls were skipped.** 55 of the 166 are disabled with nothing
   selected. A disabled button is laid out at exactly the size it will have when
   it is enabled, so skipping them measured the state of the document rather
   than the size of the interface.
3. **The key for a control with no id collided.** It was tag, class and two
   named data attributes, which for two class-less buttons is the same string,
   and the sweep dedupes on it. Found by adding two buttons to the status strip
   and watching the total stay at 138. It had been merging 28 controls into
   other rows.

The recorded figure was **84 of 85 under 44 px**. The true figure at the same
commit was **165 of 166**. Nothing had regressed; the tool had never been
counting what it said.

**The lesson is not "check the tool".** It is that a measuring tool needs a
number it cannot fake. Every one of these was found by a total that failed to
move when the interface did, which is the only signal that was ever available.
The tool now prints the total alongside the count for that reason.

## A defect the tests found first

**Two fingers landing on the same spot froze the pinch for the rest of the
gesture.** Distance zero is a division by zero, so `pinchMove` refused to act
below a pixel of separation -- and returned before re-baselining, which left the
remembered spread at zero. Every later move compared against zero, refused
again, and the fingers could travel the width of the screen without the camera
moving.

It was found by writing a test for the guard after a mutation sweep showed the
guard was unchecked, not by using the editor. Two fingers touching down together
is an ordinary press, so a hand would have found it in the first minute. The fix
is one line: take the new positions as the baseline instead of returning.

## Tests that could not fail

Eight mutations were applied to the new code, one at a time, with the whole
suite run against each. Five survived at first. Four are now caught and the
fifth is recorded below.

### 1. The second finger not abandoning the first one's drag

The test pinched over a shape but never dragged before the second finger landed,
so there was no edit to roll back and nothing to see. Rewritten to move a node
first, and to check afterwards that a later edit is still undoable -- which is
the half of that guard with no visible symptom.

### 2. A pointer type asked in two places

The second finger was identified by `pointerType` in `onDown` and again in
`onMove`, so removing either left the other holding the behaviour up. What
counts as a finger is decided once now, in `onDown`, and everything downstream
goes by membership of the map. The test that could not fail was a pen and a
mouse pressed together; it fails properly against the single guard.

### 3 and 4. The degenerate spread, and the cancelled finger

Neither had a test at all. Both do now, and finding 2 above came out of writing
the first of them.

### 5. A third finger, which is kept undistinguished

Removing the guard against a third press changes nothing observable. The palm
does start a marquee -- measured, not supposed -- but its moves are swallowed
while the pinch is live, and the first of the other two fingers to lift runs
`onUp`, whose `finally` resets the drag. Two accidents, either of which could
stop being true, so the line stays and the comment says outright that nothing
distinguishes it. The test beside it is kept as the statement of the promise and
is labelled as passing without the guard.

Same treatment as the third `meetAt` check in the review of 2026-08-14, and for
the same reason.

## A claim of mine that was wrong

`drawsSomething` was documented as refusing "a shape holding a subpath with one
node and no segment", which is what the code it replaced had claimed too. It is
not what happens: `parsePath` drops a subpath with nothing in it, so `M 0 0` and
`M 0 0 Q Q Q` both arrive with no subpaths at all, and no input to the parser
produces a subpath of exactly one node. Measured across six degenerate path
strings and five degenerate primitives.

So `>= 2` and `>= 1` were indistinguishable through the importer, and a mutation
between them survived the six tests written for it. The threshold is kept,
because the function takes shapes and is answerable for shapes that did not come
from the parser, and it is now tested against one built by hand.

## What was checked and found sound

- **The pinch, in a real browser** over CDP as well as in jsdom: 1200% to 2200%
  spreading, 1000% closing, and the viewBox origin following the fingers.
- **Double tap and long press.** A double tap reaches the app as a `dblclick`,
  so inserting a node and cycling a node's type work by tapping twice; a long
  press produces no context menu.
- **The desktop did not move.** 137 of 138 controls under 44 px to a mouse
  before the coarse block and 165 of 166 after it, which is the same interface
  measured by two different keys.
- **Every browser scenario**, rather than a sample. One fails, `traceWorker`, at
  406 ms of blocked thread against its budget. It fails identically on the
  commit before this work, so it is not from it and is not diagnosed.
- **Keyboard reachability**, unchanged at 0 live controls unreachable by Tab.

---

## The number that matters least is the one that looks best

**0 of 166 controls under 44 px to a finger.** It means the CSS says 44 px, and
nothing more. Whether 44 px is enough at this density, what the on-screen
keyboard does to a rail with eleven number fields in it, and whether a
one-finger drag on a node is worth having are all unanswered, and none of them
can be answered by the tool that produced the zero.
