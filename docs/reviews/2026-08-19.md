# Review, 2026-08-19

Covers the twenty commits since the last review: the rail redesign of 2026-08-18
and the seven feature commits of 2026-08-19 that closed the shopping list. About
5,500 lines added across 45 files, and none of it had been read by anything but
its author.

**What it found: 3 defects, 1 module with no test at all, 1 fact living in four
places, 1 comment naming code that was deleted, 5 comments restating an
architecture section that neither cites, and 2 doc blocks that lost their code.**
The defect that matters is a list of tool names that a new tool never joined,
because nothing about it was wrong -- not the types, not the run time, not any
test -- and the symptom was a preference changing on its own.

---

## A tool the session could not carry back

`src/io/session.ts` validated the restored tool name against an array:

```ts
const TOOLS: ToolName[] = ['select', 'pen', 'ellipse', 'rect', 'hand'];
```

`ToolName` gained `'poly'` on 2026-08-19. The array did not. A `ToolName[]`
accepts any subset of the union, so nothing failed to compile, and the fallback
for an unrecognised name is a legal tool, so nothing failed at run time either.

Draw with the polygon tool, reload, and the editor comes back on Select. No
message, no error, and the drawing is intact -- which is what makes it hard to
notice and hard to believe once noticed.

```
expect(back.view.tool).toBe('poly')
  Expected: "poly"
  Received: "select"
```

**The tests had the shape of this covered and still could not see it.** There is
a test that an unknown tool name falls back, and it stays green when a real tool
is left out of the list and starts falling back too. What was missing was the
other direction: every name the editor has, coming back as itself.

**Fixed as the class.** The three fields with a fixed set of values are checked
against `Record<K, true>` keyed by the union, so leaving a member out is a
compile error. Verified by removing `poly: true` again:

```
error TS2741: Property 'poly' is missing in type
'{ select: true; pen: true; ellipse: true; rect: true; hand: true; }'
but required in type 'Record<ToolName, true>'
```

`Object.hasOwn` rather than `in`, because `'constructor' in {}` is true and the
value being asked about came out of a file. A test covers that too.

## Undo after opening a workspace put the old drawing back

`applySession` replaced the document through `Store.update`, which does not touch
the history. The stacks kept the snapshots of the document that had just been
replaced, and a snapshot here is a whole document rather than an inverse
operation. So one `Ctrl`+`Z` after opening a workspace threw the opened file
away and showed the previous drawing, with no edit anywhere to explain it.

```
Expected: [ "fromfile" ]
Received: []
```

**The docstring argued the case and described the opposite of what happened.**
It said the open does not go into the history "and the history is a stack of
edits to one document rather than a stack of documents" -- which is the exact
reason the stale entries had to go, stated as the reason they could stay.

`Store.forgetHistory` empties both stacks and frees the backdrops only they were
holding. `applySession` is its only caller. Emptying before freeing is required
rather than tidy, because freeing asks what is still reachable; a test breaks
the order and goes red.

## A blocked origin was reported as a drawing that is too big

`SessionStore.write` caught every failure from `setItem` and guessed the cause
from the length of the string:

```ts
this.blocked = text.length > LIMIT / 4 ? 'too-big' : 'no-storage';
```

The two causes have different answers. A full quota is fixed by drawing less or
by **Forget saved work**. An origin with no storage cannot be fixed from the page
at all, and that is the common case here: a build of this editor is one file you
double-click, and Chromium gives a `file://` page an opaque origin where every
access throws. Anybody in that case with a drawing over 500 kB of text was told
their drawing was too big and sent to shrink something that was never the
problem.

Told apart by the error now: `QuotaExceededError`, which is the name the Web
Storage specification gives a full quota, and `NS_ERROR_DOM_QUOTA_REACHED`,
which is Gecko's name for it and the one this project's own browser tools would
produce.

## The module about how it fails had no test

`src/io/storage.ts` is 133 lines, and its own header says everything in it is
about the two ways it fails, "because the happy path is one `setItem`". Nothing
tested either one. Nothing tested the timer, the flush, or the latch. The one
browser scenario that touches it walks the happy path.

That is how the wrong-cause defect above survived being written: there was
nowhere for it to be wrong.

19 tests now, against a `localStorage` that can be told to throw. `mutate.mjs`
puts 2 survivors of 11 against it, and neither moves anything observable: one is
the boundary between `>` and `>=` at exactly the limit, which is arbitrary, and
one leaves a timer uncleared whose callback then finds nothing pending.

## Four copies of one bound

A polygon's corner count is held to 3 and 60 in `polygonSubpath`, in the field
handler in `main.ts`, in `readPolygon` in `session.ts`, and in the `min` and
`max` attributes in `index.html`. The inner ratio is the same in the first
three. Nothing fails if one is widened alone; what happens instead is a number
you can type that the generator then quietly refuses.

`clampCorners` and `clampRatio` are exported from `primitives.ts` and the other
two call them. The markup is a fourth copy that cannot import anything, and it is
named in `ARCHITECTURE.md` §63 as the one that has to be changed by hand.

## What the tests were worth

`mutate.mjs` on `src/io/session.ts` before this review: **28 survivors of 57**.
Nearly every one was a guard in the reader turned inside out, letting through
input the module exists to refuse. The 20 tests there covered the refusals by
example -- one bad coordinate, one bad fill rule, one bad axis -- and a chain of
five `||` is not one test.

After: **4 of 67**, and each of the four only changes which clause does the
refusing.

**Two of the tests written during this review could not fail, and were caught by
the same method.** A guide fixture of `'x=3'` refuses whether or not the object
check is there, because a string has no numeric `at` either; `null` is what
separates them, and it separates them by throwing, which is the failure the
whole reader is built to avoid. An angle origin written as `null` reads back as
`null` with or without the fallback it was meant to be testing.

`src/core/primitives.ts` came out at 3 survivors of 36, of which 2 mirror or
reverse a shape into a congruent one and 1 is inside a comment.
