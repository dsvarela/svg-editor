Four items from the queue `2026-08-21` filed, in the order they were asked for:
sharpen `tools/mutate.mjs`, read `src/tools/commands.ts`'s survivors, close the

The first one turned out to be the interesting one, and not in the direction it

## The skip I filed was wrong, and the check that showed it is the point

`2026-08-21` filed one line of work: teach `mutate.mjs` to skip operators inside
string, template and regular-expression literals, on the argument that
"mutating a character inside a string is noise of the same kind as mutating a
comment". It named `` `</g>` ``, `<svg xmlns=` and `/^-+|-+$/` as examples.

It was implemented. `src` went from 3 767 sites to 3 712, `src/io/svg.ts` from
163 to 131, and **all 55 removed sites were read and every one is inside a
literal**. That check passed and proves nothing, because it answers the wrong
question: "inside a literal" is not "cannot be a finding".

**The question that settles it is whether the suite disagrees**, so six of the
55 were mutated by hand and the tests they touch were run. Every one is caught:

| Removed site | What the mutation does | Suite |
|---|---|---|
| `` lines.push(`${pad}</g>`) `` | writes `<=/g>`, a file no parser accepts | 3 red |
| `const NUM = '[-+]?…'` | a negative number in a `transform` stops parsing | 5 red |
| `const RE_NUMBER = /[+-]?…/` | path data stops accepting a signed number | 116 red |
| `` `${prefix}-${++idSeq}` `` | ids become `shape+1`, which `/-(\d+)$/` cannot read back | 2 red |
| `if (s === '-0') s = '0'` | negative zero stops being normalised on the way out | 1 red |
| `.replace(/</g, '&lt;')` | `<` stops being escaped in exported text | 1 red |

**Six of six, and that is the whole argument.** A mutation inside a comment can
never be caught by anything; these are caught by between one and 116 tests each.
They are not the same kind of thing, and skipping them would have thrown away
sites that were doing exactly what the tool exists to do.

The reason is not subtle once stated. **A regular expression in a string is a
program in a small language, and a template that assembles markup is a
serialiser.** Mutating either mutates a program. The filing did not distinguish
that from a `-` in a sentence somebody reads, and neither did the
implementation, and neither did the check the implementation was accepted on.

So the skip is refused. What is kept is the scanner it was built on, which
answers a narrower question correctly.

## What the scanner is for, now that it skips nothing new

A comment cannot be found without tracking the literals around it. `'/*'` is two
characters in a string; `` `//` `` is two more; and a `/` opens a regular
expression or divides depending on the token before it. The check this replaces
judged a line at a time and got both halves wrong: it read a wrapped
block-comment line as code unless the line began with `*`, and it had no way at
all to tell a `//` inside a string from one that starts a comment.

The literals are tracked and deliberately not returned.

**On this tree the correct scanner and the line-at-a-time one produce an
identical site list**, 3 767 both ways, which is worth stating plainly: the
change removes nothing and fixes a class of misread rather than a count.

A literal that does not close on its own line was never one, so the state is
unwound at the newline rather than carried forward. What that costs is a comment
later on the same misread line, which is one noise survivor somebody reads and
discards.

Five are dark in the browser suite as well as the unit one, so nothing at all

### What was done about it

`test/commands.test.ts` is new and covers six methods chosen by consequence: the
five that change geometry with nothing behind them, and the guard that decides
where a finished trace lands. Every test asserts all three of the document, the
returned boolean and the message, which is what closes the second and third
classes rather than one instance of them.

**Measured over the same three line ranges, before and after: 51 survivors, then
14, then 6.**

| Range | Before | First pass | After reading the 14 |
|---|---|---|---|
| `offsetSelection`, `strokeToPath`, `stepNodeSelection` | 31 | 9 | 5 |
| `simplifyToCount`, `keepSelectedNodes` | 13 | 4 | **0** |
| `applyTrace` | 7 | 1 | 1 |

The middle column is the point of the second pass. **A survivor count is not a
finding until someone has read the survivors**, and reading those 14 found six
more real gaps: three boundaries the fixtures straddled without landing on
(`target < 2`, `keep.size < 3`, `next < 0`), and three refusals whose message
nothing asserted, where the operation fails a second time further down so the
`false` alone cannot say which guard answered.

One of those six tests was wrong when written. `simplifyToCount(2)` on a closed
path leaves three nodes, not two, because `reduceToCount` floors a ring at three
the way `keepSelectedNodes` says out loud. The guard's message -- "two is the
fewest a path can have" -- is true of the argument it checks and not of every
path it may be handed. Moved to an open path, where two is reachable.

The six that remain are read and none is a gap. Two are provably equivalent:
`by > 0` against `by >= 0` where `by` is typed `1 | -1`. One is unreachable:
`applyTrace`'s `if (!ok)` guards a `tryEdit` whose mutator returns `true`
unconditionally. Three need a document with an empty subpath in it, which no
fixture here can build and no importer can produce.

### One defect, and it is on the first press

**`stepNodeSelection` refuses the only route it exists to provide.** Its opening
branch reads "Nothing chosen yet: start at the first node of the first selected
shape" and it was dead: it asked `selectedNodes`, which widens a selected shape
to every node in it, so `refs` was never empty. With a shape selected the walk
started from that path's LAST node, and **Next** answered `That is the last node
of the path.` while **Previous** jumped to the second-from-last.

`main.ts` enables both buttons for a selected shape on the strength of that
branch, with a comment saying it is "how you get the first node without a
pointer". Asking `selectedRefs` -- the nodes the selection actually holds --
makes the branch live.

**And the branch had a second defect, which only showed once it ran.** It never
dropped the shape from the selection, where the walking branch below it does.
`selectedNodes` widens a selected shape to every node in it, so the panel read
the whole path back and the Node group said `8 selected` beside a selection of
one.

The browser suite is what found that, and it is worth saying how it had been
passing. The `keyboardNodes` scenario presses `]` with a shape selected and
requires `0/0`, which is exactly the case the dead branch was for. It passed
because the starter shape is CLOSED: the old walk started at the last node,
stepped past the end, and wrapped to node 0. **The right answer by the wrong
route**, and the same scenario on an open path would have failed from the day
it was written.

### And one guard that was argued for and never reached

`applyTrace` refuses a result whose backdrop has moved since the walk began, and
the comment above it argues carefully that the comparison is exact on purpose.
`||` mutated to `&&` survived: only a backdrop that moved in **all four** numbers
would then be refused, so a nudge along one axis lands the whole trace in the
wrong place with nothing said. The new tests move one number at a time, which is
the only fixture shape that can tell the two spellings apart.

## Two files mutation cannot reach

`src/main.ts` and `src/view/rulers.ts` are the two modules no test imports, so
`vitest related` runs nothing for them and every mutation would survive by
construction. Read instead. Four findings, one of which a person sees.

### The ruler labels carry one decimal too many

`src/view/rulers.ts` rounds each label to its step's own precision:

    const dp = Math.max(0, Math.ceil(-Math.log10(t.step) + 1e-9));

The epsilon is there to stop float error in `Math.log10`, and it is added in the
direction that makes the error rather than absorbing it. At an exact power of
ten `-Math.log10(step)` is an integer, and `Math.ceil` of an integer plus a
positive epsilon is the next integer up. **At a step of 1, which is the default
grid, every label on both rulers reads `10.0` where it means `10`.** At 0.1 they
read `1.20`. Five of the 27 steps on the 1-2-5 ladder are affected and all five
are the powers of ten.

Subtracting the epsilon is correct in both directions: `0.9999999999999998` and
`1.0000000000000002` both `ceil` to 1.

Nothing could have caught it. `rulers.ts` has no unit test, and the `guides`
scenario reads its labels through `+e.textContent`, which turns `"10.0"` into
`10` before comparing. The fix moves the arithmetic to `rulerTicksFor` in
`src/view/viewport.ts`, which is where the step is chosen from the ladder and
which `test/grid.test.ts` already covers.

### The bend looseness floor is spelled three times

`0.05` is the smallest looseness a bend may have, and it is written in
`src/main.ts`, in `src/tools/commands.ts` and as the `min` on the field in
`index.html`. The two TypeScript copies are the field route and the key route
into one operation, which is exactly the shape §71 found in the slide margin and
fixed by exporting `SLIDE_MARGIN`. Same fix here.

### A refusal that names the wrong reason

`traceBackdrop` opens with

    if (!b || tracing) {
      say('Load an image in the Backdrop panel first.', false);

Two conditions, one sentence, and it is false for the second: a trace already
running is not a missing image. The button is disabled while a trace is in
flight, so the branch is unreachable through it today, which is why nobody has
read the wrong sentence.

### A value computed and voided

`const group = head.closest('.group')` in the group-collapsing loop is read by
nothing but the `void group;` two lines below it, and the same call is already
made one line above for `body`. `code` rule 13.

## The two `svg.ts` gaps, and one of them was filed wrongly too

### A rect's two radii were interchangeable

`2026-08-21` filed this as "no test asserts a rounded rect's exact path data".
Literally true and not the gap. The gap is that **every rect fixture in the file
sets `rx` and `ry` to the same number**, or sets one and lets the spec copy it,
and while they agree the two are interchangeable everywhere in that branch: swap
them in all eight places the template writes them and all 111 tests still pass,
while an `<rect rx="8" ry="2">` imports rounded the wrong way round. The
fixture-too-simple class, and the same one `2026-08-19d` found in `ops.test.ts`
where every path started at the origin.

Two tests now, both measuring the radii off the drawing: the straight run along
the top starts `rx` in from the corner and the run down the left side starts
`ry` down from it, so the two distances name which radius went where. The second
covers the clamp, which is per-side and which a square cannot tell apart.

**The first version of that clamp test could not fail.** It compared
`rect rx="9" ry="9"` on a 20 by 6 box against `rect rx="9" ry="3"`, and a
mutation to the clamp degrades both sides identically, so it passed either way.
That is the exact trap the comment four lines above it already warns about, in
the same file, about the same function. Rewritten to measure, it goes red on
both halves of the clamp.

### A negative number in a transform

Confirmed as filed. Every `parseTransform` fixture was positive, so the `[-+]?`
at the head of the number pattern decided nothing. Dropping the sign makes
`translate(-10 -20)` read as `translate(10 20)`, which puts the drawing on the
wrong side of both axes, and it left the whole file green. A
`<g transform="translate(-40 0)">` is ordinary in a hand-written file.

Three tests: a negative number, an explicit plus with an exponent of either
sign, and a negative rotation. Dropping the sign now fails five tests.

## What the angle-step comment claims and the code does not

`src/main.ts` clamps the angular snap step with `Math.max(0, …)` under a comment
saying it is "clamped above zero because a step of 0 asks for infinitely many
rays". Neither half is true. The clamp permits zero, and zero does not ask for
infinitely many rays: `nearestRay` returns `null` on `!(s.step > 0)` and the
`#angleinfo` readout says `no step`. A step of 0 is a supported state with a
guard and a readout, the same shape the grid step has.

The comment is the finding. It sits exactly where a reader's question is and
answers it wrongly, which is the `comments` rule 2 shape.
