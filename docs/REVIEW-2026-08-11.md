# Review of `e6295c7..92b9476` — 2026-08-11

The range is one commit: primitive tools, circularise, rename, tooltips.
+1079 / −61 across 15 files plus 3 new ones. It was code-complete — typecheck
clean, 266 tests green, 16 browser scenarios green — and none of that is a
review. This is the review.

Four read-only lanes, scoped off the diff rather than off the feature list:
**GESTURE** (`controller.ts`), **WIRING** (`main.ts`, `tooltip.ts`, markup and
CSS — the set that shipped with no unit test), **CALLSITE** (how the new
geometry is *called*, plus whether the new tests can fail), and **RECORD** (the
prose, the comments, and the browser harness). About 95 raw findings, heavily
overlapping; deduplicated into the classes below.

No lane came back clean. Every load-bearing claim below was checked against the
source or measured, not accepted on the strength of the report.

## Prediction versus outcome

Five named risks were written down before dispatch. All five landed — but the
two most serious defects in the range were in neither list: **the documentation
asserts things the code does not do**, and **the browser scenario written to
cover this range asserts nothing at all**. Both are the same class the register
already names — *an instrument whose condition is wrong reports green while
measuring nothing* — and prose is an instrument. Predicting the code and
forgetting the record is the lesson worth keeping.

## Class 1 — An operation that reports "nothing happened" after changing the document

The worst class here, because the status line is the only thing telling the user
what happened, and it is lying.

| Site | Instance |
|---|---|
| `src/model/ops.ts:142` | `setContinuity` runs both `??= latentHandle(...)` **before** the guard on :144 rejects the operation. At an end of an open subpath one latent position does not exist, so the other handle is assigned and the function bails. |
| `src/tools/controller.ts:1269` | `setSelectedContinuity` opens `store.edit` — checkpoint, then mutate — before knowing whether anything will change. |
| `src/tools/controller.ts:642` | `circulariseSelection` does the same; a collinear selection reports "no circle is determined" and still pushes an undo entry. |
| `src/tools/controller.ts:501` | The double-click continuity cycle inherits :142 and never leaves `corner`, pushing a history entry per dead click. |

**Measured.** `M0 0 (hOut 4,6) → L10 0`, Smooth on node 1: `hIn` becomes
`[6.667, 0]` and the rendered segment moves by **1.481 units**, while the
controller reports *"That node is an end of the path — there is no second handle
to line up with."* The decline is announced for an edit that was committed.

It also breaks a stated invariant. ARCHITECTURE §3 says a straight segment has
no handles and `segmentIsLine` is two `=== null` checks. After this call a
straight segment carries a handle, so the model has permanently forgotten that
the segment was a line and `L`/`H`/`V` recovery is gone for it.

**Structural fix, not four patches:** decide before mutating. `setContinuity`
should compute the target handles and either commit both or touch nothing, and
the store should grow a form that discards its own checkpoint when the mutation
turns out to be a no-op. One change closes all four sites.

## Class 2 — A closed contour whose spans must sum to ±2π, with nothing making them

`src/model/ops.ts:472`. Each inter-node angle is normalised into (−π, π], which
is right for the common case and wrong whenever a closed contour has a gap wider
than 180°: the closing arc is rebuilt sweeping *backwards*, and the result is a
retraced petal rather than a circle.

Found independently by two lanes with different fixtures, and confirmed here:

| Fixture | `moved` reported | What the shape became |
|---|---|---|
| Closed, nodes at 0° 20° 40° 60° | `3.6e-15` | spans sum to 0, not 2π — the path traces out and back |
| Closed, nodes at 0° 60° 120° | `0` | a 120° arc plus a bulging retrace of it |

The status line says *"furthest node moved 0"* — which is true, and reads as a
perfect result on a destroyed shape.

**The existing tests cannot catch it, and neither can the metric.** Sampled
radial error on the first fixture is `2.4e-4` — every point genuinely *is* on the
circle. Roundness is blind to a retrace. Catching this needs a different
property: that the normalised spans of a closed contour sum to ±2π, or that the
enclosed area is πr².

## Class 3 — Two things that must agree, with nothing making them agree

Every instance here is prose or markup asserting something the code does not do.

| Claim | Where | Measured |
|---|---|---|
| "A handle sitting on its own chord leaves that segment the same straight line… the drawing does not jump" | `ARCHITECTURE.md:125`, the commit message | False. The handles are placed on the chords and then rotated to the *averaged* direction, which pulls both off. A right-angle corner on 10-unit sides bows by **1.48 units**. |
| "Clicking one moves the handles to make it so" | `README.md:97` | Smooth on a corner with equal neighbouring chords yields **symmetric**, because each materialised handle is ⅓ of an equal chord. |
| "Cycle corner → smooth → symmetric" | `README.md:55` | On a square, a regular polygon, or any node with equal chords, `smooth` is unreachable — a two-state toggle. |
| "Two cases still have nothing to do, and both now say so" | `ARCHITECTURE.md:129`, `README.md:100` | There are at least **five** silent no-ops. `corner` on a corner, `symmetric` on a symmetric node and `smooth` on an already-smooth node emit no message at all. |
| "the exact handle length for a circular arc" | `ARCHITECTURE.md:284` | An approximation. At a 180° span the radial error is **1.8e-2**, 67× the quarter-arc figure that `primitives.ts:14` records correctly in the same commit. |
| "unevenly spaced ones come out as round as evenly spaced ones" | `ARCHITECTURE.md:286`, `README.md:123`, `SHOPPING-LIST.md:55` | False, and the doc's own example is the counterexample: 5 nodes at 0/10/20/140/260° give **1.54e-3** against **2.73e-4** for four even ones — 5.7× less round. `test/primitives.test.ts:244` already asserts the looser bound, so the test and the prose contradicted each other on arrival. |
| "Drag the outline → move the whole shape" | `README.md:53` | Now conditional; see Class 8. |
| "anything that will not fit is hyphenated" | `README.md:169` | `xmlId` also prefixes `n` before a leading digit and falls back to the literal `shape`. |

Non-prose instances of the same class: the tooltip key-cap regex requires a
*trailing* parenthesis while `index.html:100,103` put the shortcut mid-string, so
the two buttons the feature shipped for are the two that do not get a key cap;
`index.html:184` declares `#drawinfo` and nothing ever writes to it; the toolbar's
smooth/symmetric glyphs draw hollow handle dots, which in the canvas vocabulary
mean a *latent* handle, so the Smooth glyph reads as a corner.

**Structural fix:** the numeric claims should be assertions. A doc sentence that
states a bound is a test that has not been written yet.

## Class 5 — A gesture that can end without ending

`src/tools/controller.ts`. The worst outcome in the range: **undo can die
silently for the rest of the session.**

- `:216` `onDown` has no re-entry guard, so a second pointerdown overwrites
  `this.drag`. `:481` then infers whether to close the batch by inspecting the
  *current* drag, reads the fresh one, and skips `endBatch()`. `store.ts:130`
  makes `checkpoint()` a permanent no-op while `batch > 0 && batchTook` — so no
  undo point is ever recorded again, with no signal.
- `:94` routes `pointercancel` to `onUp`, so a cancelled gesture **commits** a
  half-drawn primitive. Escape and pointercancel express the same intent and do
  opposite things.
- `:217` a right-click during a left-button drag ends the drag and commits it.
- `:220` `setPointerCapture` is unguarded; if it throws, `onDown` aborts before
  `this.drag` is set.

**Structural fix:** `onDown` returns early while a drag is live; track "this
gesture opened a batch" as a field rather than re-deriving it at `onUp`; route
`pointercancel` to an abort path.

## Class 6 — Keyboard dispatch that does not agree on modifiers or focus

- `controller.ts:846` — bare-letter tool bindings never consult the modifier, so
  **Ctrl+E opens the source drawer *and* silently switches the tool to Ellipse.**
  Confirmed in a live browser. `Ctrl+R` does the same, masked by the reload.
- `main.ts:74` — the Ctrl+E/Ctrl+B handler has no `INPUT`/`TEXTAREA` guard, and
  the collapsed drawer is `height: 0; overflow: hidden`, not `display: none`, so
  the textarea **keeps focus**. Typing continues into an invisible field, and
  because the subscriber skips refreshing while it has focus, reopening the
  drawer shows the stale text.
- The same handler does not exclude `shiftKey`, so `Ctrl+Shift+B` is swallowed.
- `e`/`r` switch tools mid-drag while the in-flight drag keeps building the old
  primitive.

## Class 7 — A name that must be unique, with nothing enforcing it

The only class that puts **invalid output in a file the user saves**.

- `src/io/svg.ts:281` emits `id="${xmlId(s.name)}"` with no uniqueness check.
  `xmlId` is not injective: `a b`, `a-b` and `a/b` all become `a-b`. Two shapes
  named `ring` produce two `id="ring"` attributes.
- Reachable without renaming anything: `main.ts:484` names every copy
  `${sh.name} copy`, so duplicating one shape twice yields two `starter copy`.
- `src/io/svg.ts:277` — `fill` and `stroke` are user-controlled free text from
  import and are still interpolated **raw**. A fill of `a"b` produces an SVG that
  will not re-parse. Pre-existing, and exactly the failure `xmlId` was added to
  prevent.

**Structural fix:** export is the single place ids are emitted. Dedupe and escape
there, and no caller can get it wrong.

## Class 8 — Selection rules that disagree about what "selected" means

- `controller.ts:302` — **a regression introduced by this range's own fix.**
  Grabbing an outline while *any* node of that shape is selected now drags those
  nodes alone. Select one vertex of a square, drag the outline: one corner tears
  away and the shape stays put. The intended rule was the marquee case; the
  implemented rule is "any node at all". The new test only covers the
  all-nodes-selected case, where the distinction cannot show.
- `main.ts:453` — the list's click handler matches `closest('li')` and the rename
  input is inside that `li`, so clicking in the text field toggles the shape's
  selection and clears the node selection.
- The same handler toggles, so the **second click of a rename double-click
  deselects the shape.**
- `main.ts:571` — `blur` commits and rebuilds the list, so renaming one shape and
  immediately double-clicking the next reintroduces the detached-row bug this
  range's commit message claims to have fixed.

## Class 9 — Degenerate geometry admitted

- `controller.ts:564` — the zero-area guard is gated on `!d.id`, so a drag that
  returns to zero width or height **commits** a degenerate shape.
- `:554` — Shift-constrain takes `Math.min(|dx|,|dy|)`, so an axis-aligned moment
  mid-drag collapses an existing shape to a point.
- `:550` — `createDrag` is the only drag that calls `snap()` with no `exclude`,
  so the primitive's own nodes capture the cursor and it resizes in
  snap-threshold jumps.
- `primitives.ts:82` — at the radius clamp, `rectSubpath` returns coincident
  duplicate nodes and two zero-length segments.
- `ops.ts:459` — a node at the fitted centre gives `atan2(0,0)` and is teleported
  to angle 0, landing on top of another node.
- `ops.ts:142` — on coincident nodes the latent handle lands on the anchor, so
  the node keeps a zero-length handle that cannot be grabbed.

No NaN reaches the document from any new code — `fitCircle` rejects non-finite
input, all-identical points and fewer than three points; `cornerRadius` is
clamped in both `main.ts` and `rectSubpath`.

## Class 10 — The new chrome is not reachable without a mouse

- `tooltip.ts:27` — `adopt()` moves `title` to `data-tip` and never restores it,
  deleting each control's accessible *description*, while the `role="tooltip"`
  div is referenced by no `aria-describedby`. The modifier hints on the two new
  tool buttons become unreachable by assistive technology.
- The collapsed source drawer keeps its textarea and its Apply/Copy/Download
  buttons **in the tab order**, so Tab lands on invisible controls and the
  tooltip layer pops a zero-delay tip for a button that is off screen.
- There is no keyboard path to rename a shape at all: `<li>` rows are not
  focusable and `dblclick` is the only entry point.
- `aria-selected` is set on plain `<li>` in a `<ul>` with no `role`, where it is
  ignored, so the sighted and non-sighted views disagree.

## Also filed, lower

`installTooltips` leaks one `keydown` listener per call (five of its six
listeners are named references and dedupe; that one is a fresh arrow).
`out()` hides on any unrelated `pointerout` anywhere in the page, so mouse
movement dismisses a keyboard-triggered tooltip. `focusin` shows with zero delay
and browsers focus a button on click, so the capture-phase `pointerdown → hide`
is immediately undone. The tooltip's `y` is not clamped to the viewport, while
`x` is. An empty rename is discarded with no message. `nextId` is consumed twice
per primitive, so a shape's name and id can never match. `gridreadout` reports
`drawn only` from `snapToGrid` alone, ignoring `showGrid`. The cursor readout is
never recomputed when the camera moves, so it lies after a zoom until the
pointer moves. The corner-radius field accepts `1e` as `0` while still showing
`1e`. Three stale comments describe code the same commit replaced —
`main.ts:518` and `:526` describe the rebuild-churn bug this range fixed, in the
present tense; `tooltip.ts:24` documents a registry that does not exist;
`primitives.ts:68` says null handles keep corners square, which they do not (they
keep *sides* straight); `drive.mjs:106` says modifiers are sampled at press time,
which is false for the create drag added here.

## What was checked and is sound

- No NaN path into the document (Class 9).
- The `body` drag shares one delta, so a multi-shape drag translates rigidly and
  does not deform; the `shapes`/`refs` filter is exhaustive and no node moves
  twice; stale refs are guarded.
- `xmlId` is safe against attribute injection — the whitelist eliminates quotes
  and angle brackets before interpolation.
- The tooltip's capture-phase listener never calls `preventDefault` or
  `stopPropagation`, so it cannot swallow a canvas gesture; `.on` transitions
  opacity only, so the measurement is not taken mid-transition; `position: fixed`
  correctly escapes `body { overflow: hidden }`.
- `listSignature` genuinely covers everything a row renders — no document change
  was found that alters a row's appearance without changing the signature.
- Every figure in the README is accurate: 266 tests, 130.55 kB / 41.83 kB, 5891
  lines, 19 files, 16 scenarios, KAPPA and the 0.027 % quarter-arc error.
- The harness viewport reasoning is true: the canvas aspect measures 1.652 with
  the inspector open, against the 1.65 the comment claims.

## Fixed

The first wave took the top six classes. Four were closed by one structural
change each rather than a patch per site, which is the whole reason for grouping
them:

| Class | Structural change | Sites closed |
|---|---|---|
| 1 — mutation announced as a decline | `Store.tryEdit` takes a mutation that reports whether it changed anything and takes its own checkpoint back when it did not; `setContinuity` works on candidate handles and returns a boolean | 4 |
| 2 — a ring whose spans must sum to a turn | `circulariseSubpath` picks one winding from the polygon's area, forces every span to follow it, and refuses a node order that is not a ring — deciding everything before it mutates | 1, plus the centre-node and star cases |
| 5 — a gesture that ends without ending | `onDown` refuses to start a second drag; `batchOpen` records the fact rather than reconstructing it; `pointercancel` and Escape both route to `abortDrag`, and `Store.rollback` restores without offering a redo | 4 |
| 6 — keyboard dispatch | one `if (mod) return` before the bare-key switch, and undo refused mid-drag | 3 |
| 7 — invalid saved output | `uniqueXmlId` and `xmlAttr` at the single place ids and styles are written | 3 |
| 8 — what "selected" means | the outline-drag test is now "was the *whole* shape selected", not "any node of it" | 1 |

Also fixed: the create drag no longer snaps to the shape it is drawing, no
longer commits a zero-area shape, and no longer collapses under Shift; the
shortcut moved to the end of the two tool titles so the key cap renders.

**Class 4 is why the rest is believable.** The `primitives` scenario now asserts
— sizes come from the browser's own `getBBox`, the dented and circularised paths
are compared, Ctrl+E is checked not to switch the tool, and the key cap is
exercised on a control that has one. The test that could not fail on the defect
it named was rewritten with the fixture that reaches the branch.

Every new test was watched going red with the fix reverted, rather than trusted
because it passed. The wrap-around and duplicate-id tests were falsified by
hand; the assertion helper in the harness caught a bug in *itself* on first run,
reporting a 24×25 rectangle as 65×65 because it split `H`/`V` coordinates into
pairs.

### Second wave

Classes 3, 8, 9 and 10 are now closed too.

- **Class 10, accessibility.** A collapsed panel is `inert`, which removes it
  from focus, hit-testing and the accessibility tree at once, and focus inside
  it is dropped as it closes. The tooltip points its control at itself with
  `aria-describedby` while shown, restoring the description `adopt()` takes
  away, and is `aria-hidden` the rest of the time rather than sitting in the
  tree holding the last thing anyone hovered. Its vertical position is clamped
  like its horizontal one. `installTooltips` is guarded, so the `keydown`
  listener stops leaking one per call. The shape list is a `listbox` of
  `option`s, which is the role that actually carries `aria-selected`, and it
  takes arrows, `F2` and `Enter` so renaming no longer needs a pointer.
- **Class 8 remainder.** Clicking inside the rename field no longer changes the
  selection, and a plain click selects rather than toggles, so the second click
  of a rename double-click stops deselecting the shape.
- **Class 3 remainder.** `#drawinfo` says what the corner radius is. The grid
  readout no longer claims `drawn only` when the grid is hidden, which was one
  readout describing two settings and getting both wrong. The smooth and
  symmetric glyphs draw their handles filled, matching the canvas, where hollow
  means a handle that does not exist yet.
- **Class 4 again.** The `chrome` scenario measures the initial panel state
  instead of returning a hard-coded literal that no production change could
  contradict, asserts the page does not scroll (which README and ARCHITECTURE
  both already claimed it did), and checks both that a collapsed panel is out of
  the tab order and that a shown tooltip describes its control.

One finding is closed by decision rather than by code, and is recorded here so
the next audit does not re-find it: `nextId` is consumed twice per primitive, so
a shape's name and its internal id can never carry the same number. Nothing
collides, the counter is monotonic, and the exported `id` comes from the name.
Not worth a change.
